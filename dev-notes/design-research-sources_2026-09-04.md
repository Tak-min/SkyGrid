## Synthesis — actionable takeaways by redesign item

### 1. Today screen: pre-capture card + "Free" badge demotion

- **Anchor in a real photo, not a gradient.** Sources #1 (Camera Control HIG — minimize viewfinder distraction, let the subject carry the screen), #27 ((Not Boring) Camera — distinctiveness from material/tactile identity, not gradients), and #28/#29 (Tide Guide — the app's real subject matter *is* its palette) converge on the same point from three independent angles: the fix already directionally chosen in `.loop/VISION.md` (anchor in yesterday's actual photo, heavily darkened) is consistent with what currently wins design recognition on iOS, not a stopgap. Fall back to the existing gradient only on day 1/cache-miss, per VISION's own caveat — don't invent a photo.
- **Demote the Free badge using significance-matched feedback.** Source #4 (Feedback HIG: match delivery to significance) directly supports moving a low-significance, always-on billing indicator (`"Free"` badge) off the primary screen, freeing that visual weight for the streak/reveal state that is actually the reason the user opened the app that morning.
- **Keep the motion light.** Source #9 (Animation HIG mirror) bounds any new reveal/transition animation on this screen to "quick, precise," with a Reduce Motion fallback — relevant since the pre-capture card redesign will likely add a subtle photo-reveal or darken transition.

### 2. Buddies tab: invert the hierarchy

- **Never let the tab's content be just an explainer.** Source #6 (Tab Bars HIG: never hide/disable a tab for being empty; show real state) is a direct HIG-level argument against the current design (3-step explainer card before any real state) — the tab must render actual circle state even at zero buddies, with the invite CTA as the empty state's content, not a substitute explainer.
- **Lead with relatedness, not achievement or explanation.** Source #47 (NN/g self-determination theory: relatedness is a distinct engagement driver from competence) supports the P0 direction already scoped in the assessment: streak + posted-today tri-state + handle must be visible without a tap, because relatedness has to be *seen*, not read about.
- **Use a small, consistent glyph set for the tri-state, not text labels.** Source #41 (Swarm's mayor-crown redesign) and #8 (SF Symbols HIG: outline variant for list rows with text) together support representing `sealed`/`posted`/`notYet` as one distinct SF Symbol per state next to the handle, matching the existing repo convention rather than inventing new iconography.
- **Cap the circle deliberately, and justify the number.** Sources #50/#51 (Dunbar's 5-person "support clique," and Dunbar's own caution that digital tools don't raise the cognitive ceiling) give the Opus assessment's proposed cap of ~8 an external anchor: it's set intentionally above the tightest 5-person layer (room for real friend variability) but the sources argue against ever raising it casually on the assumption that "more circle members = more engagement" scales indefinitely — treat any future cap increase as its own bet with its own exit condition, per Bet 2's structure.
- **The row's destination should be the relationship.** Sources #33/#34 (Streaks: "no avatar, no story, streak count as the only game") and #37 (Locket review: no follower/like counts) both reinforce keeping the redesigned row's primary action free of any moderation/administrative framing (Block/Report moves to swipe/overflow, per the assessment's P0) — the row's job is to show the relationship, not to police it.
- **Silence on membership changes, where relevant.** Source #49 (Instagram Close Friends: silent add/remove) is a pattern to keep in mind if a future circle-membership indicator is added — do not default to notifying existing members "so-and-so joined" as a broadcast; that's a separate decision from the (already-planned) inviter-side "your invite was claimed" notification.

### 3. Onboarding: fix the stale promise, show the mechanic, add invite, cut steps

- **Fix the copy first — it's a factual bug, not a design opinion.** `WelcomeView.swift`'s "its color becomes one quiet day in your grid" line is verifiably false against the current codebase (commit `82f39a3` converted the product from averaged color to actual photos); source #13 (BeReal's own App Store description leads with the *actual* dual-camera mechanic in its first sentence) is the comparator: the fix is not stylistic softening, it's making the first screen's claim match the product.
- **Show the mechanic, don't narrate it.** Source #12 (BeReal onboarding teardown: users land in the real Friends/Profile/Home screens rather than being told about them) is the strongest single precedent for VISION's planned "two sealed discs → both unseal" onboarding step — the comparator app's whole onboarding philosophy is functional demonstration over description, and source #2 (Onboarding HIG: "teach through interactivity") is the platform-level backing for the same move.
- **Put the invite step last and make it skippable, but treat it as a bet, not a proven pattern.** Sources #57/#58 (referral placement should follow a value moment) support the *location* choice; source #56 (Userpilot's 7 real teardowns) honestly found no example of an end-of-onboarding referral step in that specific sample — so this remains consistent with the existing VISION framing as a bet (Bet 3's logic, extended one step earlier in the funnel) with its own exit condition, not an industry-validated pattern to cite as settled.
- **Cutting `pace`/`frequency` is supported, conditionally.** Sources #31 (Structured: reduce overwhelm, clean linear shape) and #56 (Sked Social's 4-item checklist, Grammarly's short mobile flow) both support net-flat onboarding length (cut 2 steps to add 2), but VISION's own instruction to verify what `PersonalizationProfile` actually consumes downstream before cutting stands — none of these sources substitute for that codebase check.
- **Bound the new mechanic-demo animation.** Source #9 (Animation HIG mirror) again applies: the sealed/unsealed reveal demo should be quick and Reduce-Motion-safe, consistent with its use on Today.

### Where this research pass found genuine limits (report honestly, not papered over)

- Mobbin and the one BeReal UX-case-study Medium post were not retrievable (403s) — compensated by Page Flows and BeReal's own help-center/App-Store text, but a screen-by-screen visual (not just textual) teardown of BeReal's Android onboarding was not independently verified this session.
- Erly's actual onboarding *flow* (as opposed to its App Store screenshots and marketing copy) was not directly observable without installing the app — the mission-type detail (source #22) comes from a third-party screenshot mirror, which is strong evidence but is not the same as a live-flow teardown. If a pixel-exact Erly onboarding comparison is needed for the ASO note (DoD 7), installing the app directly is the more reliable next step.
- The "skippable invite step at the end of onboarding" idea has directional support (value-moment placement literature) but no example found of another app doing exactly this at exactly this point — flagged above as a bet, matching the kernel's claim-vs-bet discipline.
