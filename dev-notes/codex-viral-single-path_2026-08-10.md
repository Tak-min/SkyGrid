# Sky Grid — バズとサブスク収益に至る単一経路

調査日: 2026-08-10
前提資料: `dev-notes/codex-gtm-second-opinion_2026-08-10.md`

## 結論

**Q1 の答えは Yes。集客に金や継続的な制作時間を使う前に、招待者を保持したままインストール後にバディ成立まで運ぶ招待リンクを実装すべきである。** これは公開されたランダム化比較試験の結論ではなく、類似製品の観察事実とSky Gridの二者間価値から導く**推論**である。

致命的なのは「URLという形式がないこと」それ自体ではない。現状のハンドル完全一致が、TikTokで興味を持った1人を「実際に一緒に使う2人組」へ変える途中に、検索・入力・照合・説明という大きな摩擦を置いていることである。Sky Grid のバディロックは相手がいて初めて価値を出す。したがって現状では、仮に動画がバズっても、ダウンロードの先で製品の増殖エンジンが止まる。

選ぶ経路は1つだけである。

> **Verified の TikTok ブランドアカウント「Sky Grid」から、英語の同一フォーマット動画を毎日2本出し、「1人の Sky Buddy を誘って翌朝から7日間撮る」導線へ送る。アプリ内では招待リンクで即座にペアを予約・成立させ、翌朝の相互投稿・ぼかし解除・7日グリッド・サブスク提示までを1本のループにする。**

経路は次の一本で、別チャネルは使わない。

`TikTok短尺動画 → App Store → 1人へ招待リンク → バディ成立 → 翌朝2人が撮影 → ぼかし解除 → 7日グリッド → サブスク → 同じTikTok文脈で共有`

追加現金は **$0**。ただし、開発者の工数、既存インフラ、Apple Developer Program等の既支出は含めない。

## 調査上の表示

- **確認**: 企業・創業者の公開資料、公式ヘルプ、または当事者への同時期インタビューで確認できたもの。
- **第三者推計**: Appfigures、Apptopia、Sensor Tower、data.ai 等の推計。会社自身が検証した実数とは扱わない。
- **自己申告**: 創業者・チーム・匿名投稿者が公開したが、監査・独立検証されていないもの。
- **推論**: 複数の確認事実から本レポートで導いた判断。
- **未確認**: 公開一次情報で確定できなかったもの。数字を補完しない。

海外事例は英語で検索した。対象アプリの「最初の1,000人」「最初の10万人」については、通過日時と獲得元をその粒度で公開していないケースが大半だった。以下では、確認できた前後の実数と経路を示し、通過点自体は未確認と明記する。

### 2. リンク、ディープリンク、連絡先の何が必須だったのか

確認できた共通項は「特定のURL方式」ではなく、次の機能である。

1. 招待者または実在の友達を受取人へ引き継ぐ。
2. 受取人がインストールした後、ハンドルを聞き直さずに相手を特定する。
3. 友達追加の直後に、写真、投票、ぼかし解除など二者間の価値が発生する。

爆発例は、SMS招待、連絡先照合、学校グラフ、招待リンクのいずれかでこれを実現していた。**ハンドル完全一致だけで、写真・友達ロック型アプリが初期に大量成長した確認例は見つからなかった。**

現在のLocketも招待リンクとユーザー名の両方を案内しており、電話番号/連絡先の不一致時には正しい番号で招待リンクを送り直す。[Locket公式ヘルプ](https://help.locketcamera.com/en/articles/5859741-why-can-t-i-add-a-friend-on-locket) BeRealも現在、連絡先・検索・招待共有を併用する。[BeReal公式ヘルプ](https://help.bereal.com/hc/en-us/sections/7350306007965-Friends)

Sky Grid に必要なのは汎用App Store URLではない。例えば `skygrid.app/invite/<token>` を受け取った人が、インストール済みならアプリへ遷移し、**「誰からの招待か」を表示して同意するとペアが成立する**導線である。現在のQRが汎用App Store遷移だけなら、同じ端末上のTikTok/SMSから使いにくいうえ、相手の特定を保持できないため代替にならない。

ただし、iOSのUniversal LinkだけでApp Storeインストールをまたいだ任意トークンの自動復元を保証することはできない。$0で実装する30日版では、未インストールの受取人へ「App Storeから導入後、元のメッセージへ戻って同じリンクをもう一度タップ」または短いclaim code入力を明示し、2回目のリンクopenでトークンをアプリがclaimする。Locketの現行公式手順も、先にインストールし、元の招待リンクへ戻って再タップする方式である。[Locket公式ヘルプ](https://help.locketcamera.com/en/articles/5859741-why-can-t-i-add-a-friend-on-locket) 有料deferred-link基盤なしで「初回起動時に必ず自動ペア済み」とは約束しない。

実装は次を満たす必要がある。

- 受取人の明示同意があり、招待の期限切れ・取消・ブロック・再利用防止がある。
- インストール済みは1回、未インストールはインストール後の再タップ/claim codeで、同じ招待者に着地する。
- アプリを初めて開く、またはインストール後にリンクを再タップしてからペア成立までの中央値が60秒未満。App Storeのダウンロード時間はこの時間に含めず、最初のリンクclick→pair転換率を別に測る。
- 完了したサインアップの80%以上が、ハンドル再入力なしで意図した相手とペア済みになる。
- 連絡先全件アップロードや「5人招待しないと使えない」強制はしない。Lapseの順位上昇は再現したいが、スパム感、未成年者の安全、リンク漏洩、長期継続への悪影響は再現すべきでない。

### 3. 公開された k-factor はあるか

**対象7アプリについて、分母・期間・招待送信数・受取人のアクティベーション定義まで明示された実測 k-factor は確認できなかった。**

- Lapseの「最低5人招待」は送信数の下限であり、受取人の転換率がないので `k=5` ではない。
- Bierの「年齢が13歳から1歳上がるごとに1ユーザー当たり招待数が約20%落ちる」は本人の経験則であり、Gas/TBHの公開k値ではない。[本人の説明](https://www.lennysnewsletter.com/p/how-to-consistently-go-viral-nikita-bier)
- ウェブ上にある「Gasのk=7以上」という反復記述は、検証可能な元データへ遡れなかったため採用しない。

Sky Grid では、外部流入を2人組へ変える値と、2人組が次世代を生む値を分ける。

`pair_activation = TikTok期間に初回インストールした人のうち、最初のバディとペア成立かつ翌朝の相互投稿まで完了した人数 ÷ 同期間の初回インストール人数`

`K7_nextgen = 自分自身の最初のペア成立と相互投稿を済ませたユーザーが、その後7日以内に追加招待し、その受取人もペア成立かつ翌朝の相互投稿まで完了した人数 ÷ その世代のアクティブユーザー数`

TikTokから来たAが最初のバディBを誘うと1組になるが、BはAのアクティベーションに必要な相手であり、自己増殖の分子には入れない。AまたはBが価値を経験した後に追加で誘い、アクティブ化したC以降だけを `K7_nextgen` に数える。単なるリンク送信、クリック、インストールも分子に入れない。これで「外部流入を2倍にしただけ」と「次世代が自走した」を混同しない。

### 4. 「招待必須」と「招待任意」の成長率差

因果差を数値化した公開A/Bテストは**未確認**である。観察できる範囲では次の通り。

- 強制型Lapseは最低5人招待を入れ、約16日で総合118位から1位、約120万DLまで急上昇した。ただし強制招待だけの寄与率は不明。
- 製品成立型TBH/Gasは、学校・連絡先・SMSで友達グラフを作り、TBHは最初の学校の40%を24時間で、Gasは100万DAUを2か月以内に獲得した。
- 招待送信自体は任意のLocketでも、連絡先許可と友達追加が初期価値に必須だった。創業者投稿・UGC・招待の連結で約20テスターから初月1,000万DLへ伸びた。
- BeRealのロックは「招待しないと開始できない」ではなく「投稿しないと友達を見られない」。ただし米国展開では大学施策と5人追加を使った。
- 招待が任意であるRetroの正確な成長実数は非公開で、弱い導線でも同速度で伸びられる証拠にはならない。

したがって「招待を強制すれば必ず速い」は証明されていない。一方で、**相手の存在が価値を生む製品で、相手を一操作で連れてくる仕組みなしに爆発した例も確認できない。** Sky Grid は強制招待ではなく、1人を確実に連れてこられる任意・同意型招待を先に作るべきである。

## Q2. 予算ゼロのバズは誰が作ったか

### Locketで最も裏付けの強い経路

創業者説明と同時期の観測が最もよく一致する答えは、**「創業者本人によるブランドアカウントのオーガニック投稿が着火し、その後ユーザーUGCとアプリ内招待が増幅。有償クリエイターではない」**である。ただしTikTok/招待別の獲得アトリビューションは公開されておらず、独立監査された因果分解ではない。

創業者の説明と当時確認された時系列は次の通り。

1. Matt MossがLocketの会社TikTokアカウントに、本人とAvaがアプリを使う動画を投稿。
2. 元動画が数日で約10万再生。
3. 同じ音源・製品を使ったUGCが生まれ、英国ユーザーの1本が1日で500万再生。
4. 初期ユーザーがアプリ内から友達を招待し、2022-01-11までに200万人登録。
5. 創業者によると公開時約20テスターから初月1,000万DL。

創業者は有償インフルエンサー、TikTok広告、他媒体広告を明確に否定している。[ローンチ同時期の取材](https://techcrunch.com/2022/01/11/locket-an-app-for-sharing-photos-to-friends-homescreens-hits-the-top-of-the-app-store/) 2025年の本人インタビューでも、最初の動画は「自分とAvaが作ったランダムな動画」だったと述べている。[The Up and Up](https://www.theupandup.us/p/locket-app-genz-social-media-internet/)

よって公開証拠上、Locketを「ユーザーが勝手に最初の火を付けた例」や「有償クリエイターが作った例」と扱う根拠はない。**創業者側の説明としては、製品価値を人間関係の物語として実演し、UGCが模倣できる原型を置いた例**である。

### 2024–2026年の「ゼロフォロワー・ブランド・短尺だけ・個人iOS」事例

この条件をすべて満たし、開始フォロワー数、全投稿、何本目のヒットか、DL、課金まで一次データで監査できる成功例は**確認できなかった**。成功談は開始フォロワー数を示さない、メディア流入を含む、収益が推定、複数アカウント/複数チャネルのいずれかだった。条件を緩めず「実例がある」とは書けない。

この不完全さから導けるのは「ゼロフォロワーでも必ず当たる」ではない。共通する実務的な型は、**最初の1秒で結果を視覚化し、実際の画面または本人の関係を見せ、1フォーマットを高頻度で反復すること**である。Sky Gridには、ぼかされた相手の空が自分の撮影で一瞬に解除される、という説明不要の変化がある。ここを動画の1秒目に置く。

投稿頻度の公開根拠はOasisの1日1〜2本、Sardes AIの1日2〜3本だが、因果ベンチマークではない。本計画の「1日2本×23日」は、46回の配信試行を1チャネル内で確保する実験設計である。

## Q3. バズはサブスク収益につながるか

### 結論

**自動的にはつながらない。むしろ写真ソーシャルでは、大量DLと継続課金が分離した例の方が多い。** 両立した例は、友達との基本ループを無料で成立させた後、既に繰り返し使う人へ個人的・継続的な追加価値を売っている。

### Sky Gridで両立させる条件

現行コードも読み取りだけで確認した。`OnboardingCoordinatorView.swift` はオンボーディング末尾で `Explore Pro` と `Continue Free` を分け、購入を強制していない。`PaywallValueStepView.swift` と `PaywallFeaturesStepView.swift` は「直近30日を無料」「毎日の儀式は無料のまま」と明記し、有料価値を30日超の履歴、月単位の写真閲覧、通年共有カードに置く。一方、`PaywallEntryPoint.swift` の `AutomaticPaywallPresentationPolicy` は現状、3回目の撮影から自動ペイウォールを出し、その後は3撮影または3暦日ごとに再提示し得る。**コアを無料にして履歴を売る設計方向は正しいが、まだ3日分しかなく30日超履歴の価値を経験していない時点での頻繁な再提示は、今回のバディ経路と衝突する。**

1. **最初のバディ成立、翌朝の相互投稿、最初のぼかし解除は無料にする。** ここより前のハードペイウォールは、課金転換だけでなく招待者が次のユーザーを作る能力も同時に殺す。
2. **課金は価値を経験した瞬間に置く。** 30日実験では、少なくとも1回の相互ぼかし解除を済ませ、7回目の自分の撮影で7日グリッドが完成した直後を最初かつ実験中1回だけの自動提示点とする。現行の3回目/3日ごとの自動再提示は止め、dismiss後はこの30日コホートへ自動再提示しない。表示対象は既存のMonthly/Annualを主にし、機能の約束は実装済みの範囲に限定する。現行Proの主価値は30日超で完全に開くため、Day 7の購入は確立した転換率ではなく早期の支払意思として扱う。
3. **単独でも反復するプレミアム理由が要る。** 現行実装の「30日超の履歴・月単位写真閲覧・通年共有カード」は、友達が課金しなくても本人が受け取れるため条件に合う。追加バディ枠、ストリーク保護など未実装の約束を動画やペイウォールへ足さない。
4. **RetentionをDLより前に判定する。** 個人D7ではなく、両者が残る `paired D7` を使う。一方だけ残ってもぼかしロックの価値は消える。
5. **Lifetimeをサブスク成功に数えない。** Annual $29.99に対してLifetime $39.99は差が$10しかなく、約1.33年分で永久利用になる。長く使う合理的な人ほどLifetimeを選びやすく、依頼者の「サブスクリプション収益」と構造的に競合する。30日テストではLifetimeを主要CTAにせず、Monthly/Annualの転換を別集計する。これは価格に基づく**推論**であり、現行購入構成は未確認。

## Q4. 次の30日でやる1つのこと

### 単一経路

**「7-Day Sky Buddy Challenge」を、招待ディープリンク完成後に、VerifiedのTikTokブランドアカウント1つからオーガニック短尺動画だけで回す。**

これは「招待機能開発」と「TikTok施策」の二案ではない。TikTokから来た1人を2人組にし、翌朝の利用、再招待、サブスクまで閉じる**1本の獲得ループ**であり、招待リンクはその経路の開通工事である。

ターゲットは米英語圏の「毎朝つながりたいbest friends」だけにする。恋人、家族、習慣化、AlarmKit技術訴求などへコピーを広げない。

### 最初の7日

**Day 1–4: 招待からペア成立までを作る**

- 1人用の署名付き/推測困難な招待URLを作る。
- インストール済みならアプリでclaimする。未インストールならWebで招待内容とApp Storeを示し、導入後に元リンクを再タップするか短いclaim codeを入れる。Universal Linkだけの自動復元を前提にしない。
- 受取人へ招待者を表示し、同意後にペアを成立。期限、取消、ブロック、重複処理、漏洩時の無効化を入れる。
- 共有カードのQRも同じ招待トークンを表す。汎用App Store QRは使わない。
- ハンドル検索はフォールバックに残すが、主導線から外す。
- 最初の相互ぼかし解除が終わった後に限り、同じ仕組みで「Invite one more Sky Buddy」を一度だけ任意表示する。強制せず、ここから生まれた追加ユーザーだけを次世代として数える。
- 現行の「3回目、その後3撮影または3日ごと」の自動ペイウォールを、相互ぼかし解除を1回以上経験した7回目の自分の撮影後の1回だけに変える。dismiss後はこの30日コホートへ自動再提示しない。手動のプラン画面とオンボーディングの `Continue Free` は維持する。
- Day 4までにこのビルドをApp Reviewへ提出する。審査通過は管理不能なので、Day 7までに公開されなければTikTok投稿を開始せず、Day 30を `blocked: App Review` で終了する。承認日から勝手に23日間を再起算せず、壊れた招待版へ流入させる別経路も取らない。

**Day 5: 一本のファネルだけを計測する**

- `invite_created`
- `invite_opened`
- `invite_claimed / pair_confirmed`
- `first_next_morning_post`
- `reciprocal_unlock`
- `nextgen_invite_created`
- `nextgen_activated`
- `paired_d7`
- `day7_grid_viewed`
- `paywall_viewed`
- `monthly_or_annual_purchased`

チャネル別campaign linkは作らない。外部経路はTikTok一つなので不要。招待トークンは帰属計測のためではなく、誰とペアになるかを保持する製品データである。

**Day 6: 同意した既存テスター/自分のテスト環境で経路を壊す**

- 未インストール、インストール済み、ログアウト、既存ペアあり、期限切れ、二重タップ、別人が開く、拒否/ブロックを確認。
- 合格条件は、初回app open/インストール後の再タップ→ペア成立の中央値60秒未満、最初のリンクclickから見た完了サインアップの80%以上が正しい相手とペア済み、翌朝の双方投稿で正しくぼかし解除。
- 3回目の撮影では自動ペイウォールが出ず、相互解除済みの7回目では一度だけ表示され、dismiss後は30日コホート中に再び自動表示されないことを確認する。
- この合格前にはTikTokへ投稿しない。到達した視聴者をハンドル交換で失うためである。

**Day 7: 46本を同じ型で撮れるテンプレートを完成する**

- 長さ9〜15秒、縦動画、実際のアプリ画面と実際の空を使用。
- 0〜1秒: ぼかされたバディの空。英語overlayは **“My best friend can’t see my sky until she gets out of bed.”**
- 1〜6秒: システムアラーム → 2人が外を見る → それぞれ撮影。
- 6〜10秒: 相手のぼかしが解除され、2つの7日グリッドが並ぶ。
- 最後: **“Send this to one friend. Start tomorrow. Sky Grid on the App Store.”**
- 毎回変えるのは空、人物の手元、冒頭の一文だけ。機能列挙、創業ストーリー、編集技術の実験はしない。

### 次の23日

- Verifiedの `Sky Grid` ブランドTikTokだけに、**毎日2本、計46本**を投稿する。停止中の個人TikTok、Instagram、YouTube Shorts、Reddit、Discord、Product Huntには出さない。
- 1本目は米国東部時間の登校前、2本目は放課後〜夜を狙う。投稿時刻は途中で最適化せず23日固定し、動画hookだけを学習する。
- コメントへの回答も同じ9〜15秒テンプレートの動画で行い、別コンテンツ柱を作らない。
- **動画別**に判断できるのはTikTok内の `1秒視聴維持 → 完視聴 → 保存/共有 → profile visit` までとする。campaign linkを作らない以上、個々のhookをApp Store閲覧やactivated pairへ帰属させたとは主張しない。App Store product-page views、初回起動、activated pairは、この単一TikTok経路の**全体時系列**を公開前7日ベースラインと比較する。
- 相互解除を一度以上経験した7回目の撮影直後に、30日中一度だけ現在のMonthly/Annualを主に提示し、Lifetimeは主要CTA・成功数から外す。友達招待、翌朝投稿、最初のぼかし解除には課金を置かない。
- 23日間は広告、TikTok One発注、クリエイターDM、ASO全面改稿、新機能追加をしない。招待の致命的不具合だけ直す。

### 必要現金

**$0**

有償クリエイター、広告、景品、外部投稿ツール、キャンペーンリンクには使わない。既存ドメイン/バックエンドで招待URLを成立させられず有料ベンダー契約が必要になった場合、その購入はこの計画の権限外であり、事前確認が必要である。

### 30日後の失敗ライン

以下は業界公開ベンチマークではなく、**「最速でバズとサブスクを両方取る」という今回の目的に合わせた事前判定値**である。App ReviewがDay 7までに終わらない場合を除き、Day 30で一つでも満たさなければ、この**複合目的**に対する単一路線は失敗と判定し、追加の制作費・広告費を入れない。

1. **Buzz:** 46本の英語動画中、10万再生以上が0本。
2. **Activation:** 正しい相手とペアになり、翌朝双方が投稿した `activated pair` が累計100組未満。
3. **Virality:** Day 23までに最初の相互投稿を終えた最初の100アクティブユーザーで `K7_nextgen < 1.0`。最初のペア相手は分子から除き、相互投稿後の任意追加招待から生まれた人だけを数える。Day 24以降に資格を得た人は7日観測できないため分母に入れない。
4. **Retention:** Day 23までに開始した最初の100組のうち、開始7日目にも双方が投稿した `paired D7 < 25%`。Day 24以降の組は分母に入れない。
5. **Subscription:** Day 21までに開始し、Day 28までに7日グリッドへ到達した人から、Day 30までに有効なDay 7ペイウォール閲覧を50人以上作れない、またはその閲覧から48時間以内のMonthly/Annual購入者が3人未満、または同2プランの総予約売上が$50未満。Lifetime購入は含めない。

母数不足で3〜5を計算できない場合も、Day 30時点では成功扱いにしない。「動画が回らなかった」「ペアが作れなかった」「7日残らなかった」を、サンプル不足という言葉で先送りしないためである。3購入/50閲覧は真の転換率を精密推定する母数ではなく、30日内の早期支払意思を切る最低線にすぎない。

10万再生がなくてもK7・継続・課金が合格する可能性はある。その場合、**製品ループは検証済みだが、依頼者が同時に要求した「バズ」は未達なので複合目的として失敗**と記録する。逆に10万再生だけ達成しても、残り4項目のどれかが落ちれば「見られただけ」であり成功ではない。

明示的に却下されたcampaign linkを使わないため、Activation以降はTikTokに厳密帰属できない。30日中に行う外部施策をブランドTikTok一つへ固定し、公開前7日との全体時系列差を見るが、基準を通過しても「TikTokが因果的にこの件数を生んだ」は**未確認**と報告する。これは単一経路への集中と引き換えに残る計測上の限界である。

### なぜ他を捨てるか

- **TikTok One / 有償クリエイター:** 招待ループとpaired D7を証明する前に買ったリーチは複利にならず、数百ドルでは十分なクリエイティブ試行数も買えない。
- **Apple Search Ads:** 検索需要は拾えてもバズを作らず、ハンドル照合で止まる利用者を有料で増やすだけになる。
- **Instagramの無償DM:** 実測12件中返信0件で、創業者が制御できない他者の投稿を待つ経路である。
- **開発者コミュニティ:** 一般消費者の密な友達ペアを作れないことが確認済みで、対象外とする。
- **PR / Product Hunt / ASO単独:** 掲載・検索順位は制御しにくく、1人のDLを2人組へ変える製品ループを代替しない。
- **複数SNSへの同時展開:** 46本の学習を分散し、どのhookがTikTok上でUGC化するかを遅くする。
- **5人招待の強制:** Lapse型の短期順位は狙えても、Sky Gridに必要なのは1組の継続であり、スパムと拒否を増やす5人送信はサブスク継続と逆向きである。

## 最終判断

Sky Gridの不足は認知ではなく、**認知を二者間の価値へ変え、その二者が次の二者を作る接続部**である。Locketの教訓を「TikTokへ投稿する」とだけ読むのは半分しか正しくない。正確には、創業者の人間関係を見せた短尺が火を付け、ユーザーが同じ形式を作り、連絡先/招待がアプリ内の友達グラフへ変えた。

したがって順序は動かさない。

1. 招待リンクで1人を確実にバディへ変える。
2. VerifiedブランドTikTokの同一動画型だけで46回着火を試す。
3. 翌朝の相互投稿、K7、paired D7、Monthly/Annual購入まで一本で合否を出す。

この一本が30日基準を超えない限り、広告、クリエイター、別SNS、開発者コミュニティへ寄り道しない。
