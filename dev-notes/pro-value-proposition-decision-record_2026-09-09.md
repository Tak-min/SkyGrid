最終更新: 2026-09-09

状態: **A(静止画版)・C・B-2はCodexが実装・ローカル検証済み。B-1は見送り・不採用が最終決定(13章参照)。計測イベントは新規追加なしで確定。Firebase Functionsは2026-09-09にClaude Codeがデプロイ済み(14章)。ローカルの変更はまだcommitしていない**

対象: 課金(Pro)で得られる価値がアーカイブ閲覧・書き出しの1軸しかなく薄い、という依頼者の問題提起への対応

## 2. 問題の診断(検証済み)

現行Proの特典は `ios/SkyGrid/Sources/Paywall/PaywallFeaturesStepView.swift` で3つ:

1. 過去のセル閲覧(エントリーポイント依存の文言)
2. 月単位グリッド閲覧
3. 1年分シェアカード書き出し

いずれも「自分の過去アーカイブ」という単一軸で、(a) 報酬が数週間〜1年先、(b) 一人称で完結し社交性がない、(c) 誰にも見せられない。同ファイルには "No feature is hidden after purchase: Free remains a complete daily ritual" という文言があるが、これは`PRODUCT-MODEL.md`の意思決定履歴に対応する正式決定が存在せず、**依頼者の承認を得ていないAIによる独自の方針記述**だったことを2026-09-09に確認した。今回の決定でこの制約は撤回する。

一方、`PRODUCT-MODEL.md` バックログ#1で依頼者自身が明言する通り、プロダクトの唯一の差別化要素は「相互解禁(バディ)」である。Proの価値訴求はこの軸に一切触れていなかった。

`Circle`(バディ)は1対1のペアワイズ関係の集合であり、グループ投稿ではない(`hard-circle-cap-authority_2026-09-04.md`、`FriendRepository.swift`で確認済み)。各ペアは独立した相互解禁ルールを持つ。現在は乱用防止目的の固定上限8人が `ios/functions/src/invites.ts` の `MAX_ACCEPTED_BUDDIES = 8` でサーバー側に強制されている。バディ数はグループ人数ではなく個別関係の本数なので、無料/課金で差別化しても中身の相互解禁ルールを変える必要はない。

## 3. 狙う指標

**対象指標:** paywall到達→購入確定率(`skygrid_paywall_step_viewed` → `purchase_confirmed`)

**現在値:** 未測定(GA4は`paywall_presented`が12件・5ユーザーで判断不能な標本)

**変更しない場合の反実仮想:** Proが引き続き「自分の過去を見る」という遅効性・非社交的な価値のままであり、差別化の核であるバディ体験と接続しないため、購入率も紹介経由の成長も相互に強化し合わずに横ばいで停滞する。

**バイラルループのモデル化(該当するため必須):**

```text
Circle上限に達した無料ユーザー(6人目以降を招待したい)
  → 上限到達メッセージでProを提示
  → 購入(または既存Pro所持者が先に招待)
  → 6人目以降の招待リンクが外部へ届く
  → 受信者がアプリ内で招待を受諾する
  → 受信者が最初の空を保存し、双方が相互解禁体験を得る
  → 新規ペアの一方がまた新しい相手を誘いたくなる(繰り返し)
```

Circle上限を無料側で絞ることは招待の分母(共有される招待リンクの総数)を狭める副作用があるため、5人という値は「バイラルエンジンを実質的に狭めない範囲で、6人目以降に価値を感じさせる」という依頼者の判断に基づく。これは主張ではなくベットであり、反証条件は次章の決定ログに明記する。

## 5. 実装スコープ(決定済み範囲のみ)

### C. Circle上限の無料/課金差別化

- `ios/functions/src/invites.ts` の `MAX_ACCEPTED_BUDDIES = 8` を、固定定数から**エンタイトルメント依存の上限**に変更する。無料 = 5、Pro = 15。
- エンタイトルメント判定は `ios/functions/src/subscriptionState.ts` のサーバー側ミラー(`isPro`)を使う想定だが、同ファイルの冒頭コメントは「RevenueCatがクライアント側の権威であり、遅延したwebhookが課金機能を付与してはならない」と明記している。Circle上限のサーバー側強制はこの原則の初めての例外的利用になるため、webhookの遅延・失敗時にPro購入者が誤って無料上限で弾かれるケース、また解約後もサーバー側ミラーが古いままProのまま扱われるケースの両方を、実装時に具体的にどう防ぐか(例: クライアントからRevenueCatの実エンタイトルメント状態も一緒に送る、またはサーバー側ミラーの鮮度をチェックする)をCodex側で設計し、決定不能な場合は実装を止めて報告すること。
- `acceptBuddy` / `requestBuddy` (`ios/functions/src/invites.ts`)の`circleFull` / `buddyCircleFull`判定ロジックは、呼び出し元(claimer/inviter)それぞれの上限をそれぞれのエンタイトルメントで判定する形に変える。
- iOS側 (`FriendsViewModel.swift`, `InviteClaimView.swift`) の上限到達メッセージを、固定8人の文言からProへの導線を含む文言に更新する。
- Firestore Rulesは`hard-circle-cap-authority_2026-09-04.md`記載の通り、クライアント側での直接作成/昇格を既に禁止済みのため、上限値の変更はFunctions側のみで完結する。

### B. バディ軸の新価値(v1)

- バディの過去アーカイブ閲覧: 相互解禁済みの相手について、直近日だけでなく相手の過去のセルも閲覧できるようにする。閲覧範囲(相手の全期間か、一定期間か)は未決。データアクセス範囲を広げるため、Firestore Rulesの読み取り権限とプライバシー影響をCodex側で洗い出すこと。
- 2人分の比較ビュー/カード: 自分とバディの空を並べて見せる画面またはエクスポート可能なカード。既存の`ArchiveGrowthPreview`やシェアカード実装パターンを参考にする。

### A. アーカイブ報酬の前倒し

- 既存の1年シェアカードに加え、週次リキャップ(直近7日分の振り返り)をPro特典に追加する。年次カードの実装・文言は変更しない。

## 6. 未決(Codexが実装前に依頼者へ確認すべき点)

## 13. B-1(バディの過去アーカイブ閲覧)の不採用決定(2026-09-09・12章を撤回)

## 14. Firebase Functionsデプロイ(2026-09-09・Claude Code実施)
